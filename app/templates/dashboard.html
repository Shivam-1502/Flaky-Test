1. Empirical Flakiness / Failure Rate f_empirical
f_empirical = Total Failures / Total Executions

Meaning: Raw proportion of executions resulting in failure across all observed CI runs.
Interpretation: Near 0% indicates stability; near 100% indicates deterministic break. Moderate rates (5%–95%) indicate intermittent vulnerability.
Significance: Baseline indicator of failure likelihood, though insufficient alone to prove retry recovery.

2. Batch Flakiness Frequency f_batch
f_batch = Mixed-Outcome Batches / Evaluated Batches

Meaning: Proportion of evaluated retry batches that exhibited both pass and fail results within the same job.
Interpretation: Direct gauge of within-job non-determinism under frozen code and identical runner state.
Significance: Gold-standard criterion for confirming test flakiness rather than code regressions.

3. Flaky Retry Recovery Rate P_rec (Micro & Macro)
Micro = Total Recoveries / Total Retries
Macro = Sum(P_rec(t)) / |T|

Meaning: Likelihood that an initial test failure recovers to PASS upon subsequent rerun.
Interpretation: Micro-average pools all retries; macro-average treats each flaky test candidate equally.
Significance: Quantifies automatic CI retry effectiveness and wasted runner compute.

4. Pipeline Recurrence R_pipe
R_pipe = Pipelines with Intermittency / Total Pipelines

Meaning: Breadth of disruption across distinct CI pipeline instances and commit trees.
Interpretation: High recurrence means pervasive disruption across multiple developer branches.
Significance: Distinguishes chronic, widely-felt flakiness from localized PR-specific noise.

5. Environmental Variance sigma^2_env
Var = (1/|E|) * Sum((f_env - f_mean)^2)

Meaning: Variance in test failure rates across different OS and browser runner environments.
Interpretation: High variance indicates platform-specific concurrency or rendering quirks.
Significance: Pinpoints whether flakiness is universal or isolated to specific runners.

6. Flakiness Overhead Ratio O_flaky
O_flaky = Cumulative Retry Duration / Total Base Duration

Meaning: Relative compute time consumed by retried executions compared to baseline testing.
Interpretation: Directly reflects developer feedback delays and infrastructure billing waste.
Significance: Business impact metric for justifying engineering investment in test stability.

Deterministic Priority Formulas

FIM ranks candidates deterministically using mathematically defined scoring formulas without black-box heuristics:

Verified Flaky Score:
Priority = 0.60 * P_rec + 0.40 * f_batch
60% weight on retry recovery rate + 40% on batch flakiness frequency.
Intermittent Candidate Score:
Priority = 0.60 * (1.0 - 2 * |0.50 - f_empirical|) + 0.40 * R_pipe
60% weight on outcome entropy (peaks at 50% pass/fail) + 40% on pipeline recurrence.

Evidence Stratification Tiers

Candidates are stratified into three transparent evidence confidence tiers:

High Evidence: >= 5 mixed-outcome batches or verified fail-to-pass recoveries with consistent cross-run recurrence. High confidence for immediate triage.
Moderate Evidence: 2 to 4 verified retry recoveries. Consistent intermittent behavior warranting investigation.
Low Evidence: Single isolated intermittent occurrence. Candidate kept under observation.

To ensure research rigor, the FIM Engine executes automated validation checks before computing metrics:

1. Sequence Monotonicity

Validates that retries follow sequential order (retry_count = 0, 1, 2...) within the exact same job batch.

2. Duplicate Anomaly Audit

Identifies and isolates batches with unresolved duplicate execution counts (e.g. 3 batches audited and excluded in Playwright benchmark).

3. Strict Within-Job Scoping

Prevents false flakiness by requiring retries to share identical job ID, pipeline ID, commit, and environment configuration.

● Recovery Delta: Scenario A vs Scenario B

Holding base failures identical at 40 (3.33%), Scenario A recovers 90% of failures upon rerun, while Scenario B only recovers 20%. Scenario B wastes 767.8% more rerun execution time and 67.1% more total failed test time.

● Pipeline Consolidation: Scenario A vs Scenario D

Scenario D produces the exact same 40 base failures as Scenario A, but co-locates them across two tests in 20 shared pipelines. Consequently, only 20 pipelines fail (10.0%) in D versus 40 pipelines (20.0%) in A. Systemic clustering captures this shared infrastructure risk (100% systemic flakiness ratio).
